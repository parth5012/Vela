# What is Shizuku?

**Date:** 2026-10-01 (all sources accessed 2026-10-01 unless noted)

## TL;DR

- Shizuku is an open-source Android app + server that lets ordinary apps call privileged **system (Binder) APIs directly** with **ADB (`shell`, uid 2000) or root (uid 0) privileges**, by talking to a long-lived Java process started with `app_process` instead of spawning `su`/`adb shell` commands ([shizuku.rikka.app](https://shizuku.rikka.app/), [RikkaApps/Shizuku README](https://github.com/RikkaApps/Shizuku)).
- Created by **Rikka** (RikkaApps / "Xingchen & Rikka"); repo created 2017-05-24, first release `v2.0.0-dev` 2017-10-28 ([GitHub API](https://api.github.com/repos/RikkaApps/Shizuku)).
- Status 2026: **not archived**, 30,871 stars, but last code push 2025-06-18 and latest release `v13.6.0` is 2025-05-25 — maintained slowly, with community forks ([GitHub API](https://api.github.com/repos/RikkaApps/Shizuku), [releases](https://github.com/RikkaApps/Shizuku/releases)).
- Mechanism: user starts the Shizuku server via **root, wireless-debugging pairing (Android 11+), or a PC `adb` command**; the server pushes its `moe.shizuku.server.IShizukuService` Binder to apps, which proxy calls via `ShizukuBinderWrapper` or run code in privileged **User Services** ([setup guide](https://shizuku.rikka.app/guide/setup.html), [IShizukuService.aidl](https://raw.githubusercontent.com/RikkaApps/Shizuku-API/master/aidl/src/main/aidl/moe/shizuku/server/IShizukuService.aidl)).
- Access is gated by a **user consent dialog** (self-managed runtime-style permission) and by ADB's own limited permission set — it is *not* root and cannot do everything root can ([Shizuku-API README](https://github.com/RikkaApps/Shizuku-API), [Shell AndroidManifest](https://github.com/aosp-mirror/platform_frameworks_base/blob/master/packages/Shell/AndroidManifest.xml)).
- Reach: **10M+ Play Store downloads**, 4.3★ / 55.5K reviews; used by apps such as Canta, Droid-ify, Inure, App Ops ([Play Store](https://play.google.com/store/apps/details?id=moe.shizuku.privileged.api)).

## 1. Definition: what Shizuku is and the problem it solves

Shizuku's own one-line description: "Shizuku can help normal apps uses system APIs directly with adb/root privileges with a Java process started with `app_process`" ([introduction](https://shizuku.rikka.app/introduction.html)); the GitHub description repeats it: "Using system APIs directly with adb/root privileges from normal apps through a Java process started with `app_process`" ([repo](https://github.com/RikkaApps/Shizuku), [GitHub API metadata](https://api.github.com/repos/RikkaApps/Shizuku)).

The problem it solves, in the project's own framing: apps that need elevated rights traditionally run shell commands (`pm enable`, `pm list`, …) in an `su` or `adb shell` session. The project lists the costs of that "old school" method — each "Execute" is a new process creation (extremely slow), results must be parsed as text (unreliable), capability is limited to whatever commands exist, and "even if ADB has sufficient permissions, the app requires root privileges to run" ([README — Background](https://github.com/RikkaApps/Shizuku), [introduction](https://shizuku.rikka.app/introduction.html)).

Instead, Android apps normally reach system services over **Binder** IPC (e.g. `PackageManager#getInstalledPackages()` is really app-process → `PackageManagerService`), and Binder lets the server side see the client's uid/pid for permission checks. Shizuku starts one privileged process ("Shizuku server") with root or ADB, hands its Binder to each app process at start-up, and acts as a middleman: app → Shizuku service → system server → results back, so the transaction is performed *as* uid 2000 (shell) or uid 0 (root) ([README — How does Shizuku work?](https://github.com/RikkaApps/Shizuku), [introduction](https://shizuku.rikka.app/introduction.html)). The Play Store description calls it "an open-source app for serving multiple apps that require root/adb" ([Play Store](https://play.google.com/store/apps/details?id=moe.shizuku.privileged.api)).

Two stated purposes: (1) a convenient way to use system APIs, (2) "convenient for the development of some apps that only requires adb permissions" — i.e. letting a "root required app" that truly only needs ADB-level rights reach a much larger non-rooted audience ([introduction](https://shizuku.rikka.app/introduction.html), [README](https://github.com/RikkaApps/Shizuku)).

## 3. Technical mechanism

**Starting the server.** Shizuku supports three start methods: (a) **root** — start directly; (b) **wireless debugging** (Android 11+, no computer — pair once with a pairing code, then start on device); (c) **computer via `adb`** for unrooted Android 10 and below, using `adb shell sh /sdcard/Android/data/moe.shizuku.privileged.api/start.sh` (v11.2.0+) ([user manual — Start Shizuku](https://shizuku.rikka.app/guide/setup.html)). Android Debug Bridge itself is "a versatile command-line tool that lets you communicate with a device" ([developer.android.com](https://developer.android.com/tools/adb)). The server is a Java process started with `app_process` ([repo description](https://github.com/RikkaApps/Shizuku)).

**Wireless-debugging pairing.** Implemented in the manager with an MDNS discovery + pairing-code client (`AdbMdns`, `AdbPairingClient`, `AdbPairingService`, `AdbClient`, `AdbKey`) ([manager/adb source directory](https://github.com/RikkaApps/Shizuku/tree/master/manager/src/main/java/moe/shizuku/manager/adb)); the UI flow (enable Developer options → USB debugging → Wireless debugging → pair in Shizuku → start) is documented step-by-step in the [user manual](https://shizuku.rikka.app/guide/setup.html).

**Binder plumbing.** The service interface is `moe.shizuku.server.IShizukuService` (the `BINDER_DESCRIPTOR` constant matches this name) with fixed transaction codes, e.g. `getVersion() = 2`, `getUid() = 3`, `checkPermission(String) = 4`, `newProcess(...) = 7`, `addUserService(...) = 11`, `requestPermission(int) = 14`, `checkSelfPermission() = 15`, `attachApplication(...) = 17`, `exit() = 100`, `attachUserService(...) = 101`, plus `dispatchPermissionConfirmationResult(...) = 104` ([IShizukuService.aidl](https://raw.githubusercontent.com/RikkaApps/Shizuku-API/master/aidl/src/main/aidl/moe/shizuku/server/IShizukuService.aidl), [ShizukuApiConstants.java](https://raw.githubusercontent.com/RikkaApps/Shizuku-API/master/shared/src/main/java/rikka/shizuku/ShizukuApiConstants.java)).

- **How the Binder reaches apps:** the server observes process start-up — "combine `IActivityManager#registerProcessObserver` and `IActivityManager#registerUidObserver` (26+) to ensure that the app process will be sent when the app starts" ([README — Attention](https://github.com/RikkaApps/Shizuku)); `BinderSender.sendBinder()` then checks the app's declared permissions and delivers the Binder (`sendBinderToUserApp` / `sendBinderToManger`) ([BinderSender.java](https://github.com/RikkaApps/Shizuku/blob/master/server/src/main/java/rikka/shizuku/server/BinderSender.java)).
- **Client side bootstrap:** apps add `rikka.shizuku.ShizukuProvider` to their manifest (authorities `${applicationId}.shizuku`, protected by `android.permission.INTERACT_ACROSS_USERS_FULL`) and use `Shizuku.addBinderReceivedListener()` / `addBinderDeadListener()` to track the Binder's life ([Shizuku-API README](https://github.com/RikkaApps/Shizuku-API), [demo manifest](https://raw.githubusercontent.com/RikkaApps/Shizuku-API/master/demo/src/main/AndroidManifest.xml), [ShizukuProvider.java](https://github.com/RikkaApps/Shizuku-API/blob/master/provider/src/main/java/rikka/shizuku/ShizukuProvider.java)).
- **Proxying calls:** `ShizukuBinderWrapper` forwards Binder calls to the Shizuku service, and the server's `transactRemote()` re-issues them after `Binder.clearCallingIdentity()` — so the system server sees the *server's* uid (2000/0), not the app's ([Shizuku-API README — Remote binder call](https://github.com/RikkaApps/Shizuku-API), [Service.java](https://raw.githubusercontent.com/RikkaApps/Shizuku-API/master/server-shared/src/main/java/rikka/shizuku/server/Service.java), [README — transactRemote](https://github.com/RikkaApps/Shizuku)).

**User Services (running your own code privileged).** `Shizuku.bindUserService(UserServiceArgs, ServiceConnection)` starts a Java (or JNI) service process that runs *as* root (uid 0) or shell (uid 2000) — "like Bound services… the difference is that the service runs in a different process and as the identity (Linux UID) of root (UID 0) or shell (UID 2000)". The service class must implement `IBinder` (typically `YourService extends IYouAidlInterface.Stub`); stopping via `unbindUserService` does **not** kill the process — the service must implement a "destroy" method (transaction code `16777115`, i.e. `16777114` in AIDL) and call `System.exit()` ([Shizuku-API README — UserService](https://github.com/RikkaApps/Shizuku-API), [ShizukuApiConstants.java](https://raw.githubusercontent.com/RikkaApps/Shizuku-API/master/shared/src/main/java/rikka/shizuku/ShizukuApiConstants.java)). User-service processes are launched by a shell command of the form `CLASSPATH='<manager apk>' … /system/bin --nice-name='…' moe.shizuku.starter.ServiceStarter --token=… --package=… --class=… --uid=…` ([ServiceStarter.java](https://github.com/RikkaApps/Shizuku/blob/master/starter/src/main/java/moe/shizuku/starter/ServiceStarter.java)).

**Server lifecycle / permission model.**

- Server version constants: `SERVER_VERSION = 13`, `SERVER_PATCH_VERSION = 6` ([ShizukuApiConstants.java](https://raw.githubusercontent.com/RikkaApps/Shizuku-API/master/shared/src/main/java/rikka/shizuku/ShizukuApiConstants.java)).
- The server requires the manager app (`moe.shizuku.privileged.api`) to be present and exits with `MANAGER_APP_NOT_FOUND` otherwise ([ShizukuService.java](https://github.com/RikkaApps/Shizuku/blob/master/server/src/main/java/rikka/shizuku/server/ShizukuService.java)).
- Every API call goes through `enforceCallingPermission()`, which throws `SecurityException` for callers that are not attached clients or whose `ClientRecord.allowed` flag is false ([Service.java](https://raw.githubusercontent.com/RikkaApps/Shizuku-API/master/server-shared/src/main/java/rikka/shizuku/server/Service.java)).
- **Consent dialog:** `requestPermission(requestCode)` either replays an existing decision or calls `showPermissionConfirmation()`, which launches the manager's `RequestPermissionActivity` (action `${applicationId}.intent.action.REQUEST_PERMISSION`); the user's answer returns via `dispatchPermissionConfirmationResult()` and flips `ClientRecord.allowed` ([Service.java](https://raw.githubusercontent.com/RikkaApps/Shizuku-API/master/server-shared/src/main/java/rikka/shizuku/server/Service.java), [manager AndroidManifest.xml](https://raw.githubusercontent.com/RikkaApps/Shizuku/master/manager/src/main/AndroidManifest.xml)). API-side the flow mirrors runtime permissions: `Shizuku.checkSelfPermission()`, `Shizuku.requestPermission()`, `shouldShowRequestPermissionRationale()`, plus `addRequestPermissionResultListener()` ([Shizuku.java](https://raw.githubusercontent.com/RikkaApps/Shizuku-API/master/api/src/main/java/rikka/shizuku/Shizuku.java), [Shizuku-API README](https://github.com/RikkaApps/Shizuku-API)).
- **Start on boot:** a `BootCompleteReceiver` handles `BOOT_COMPLETED`/`LOCKED_BOOT_COMPLETED`. Root mode restarts the server via the starter command; **ADB mode auto-start only on Android 13 (TIRAMISU)+** and only if the app already holds `WRITE_SECURE_SETTINGS`, in which case it flips `adb_wifi_enabled`/`ADB_ENABLED`, discovers the local wireless-debugging port over MDNS and runs the starter command through an `AdbClient`; otherwise it logs "No support start on boot" ([BootCompleteReceiver.kt](https://github.com/RikkaApps/Shizuku/blob/master/manager/src/main/java/moe/shizuku/manager/receiver/BootCompleteReceiver.kt)). The relevant preference keys are `start_on_boot` and the stored launch mode (`ROOT`/`ADB`) ([ShizukuSettings.java](https://github.com/RikkaApps/Shizuku/blob/master/manager/src/main/java/moe/shizuku/manager/ShizukuSettings.java)).

## 4. API surface

- **Distribution:** Maven artifacts `dev.rikka.shizuku:api` and `dev.rikka.shizuku:provider` (latest documented version **13.1.5**), published on Maven Central ([Shizuku-API README](https://github.com/RikkaApps/Shizuku-API)).
- **API/server versions:** `Shizuku.getServerVersion()` returns `SERVER_VERSION` (13); `Shizuku.isPreV11()` exists for legacy gating; changelog documents breaking changes at v11 (permission model), v12 (dropped pre-v11), v13 (`Context` constructor for user services), and 13.1.0 (desugaring required for minSdk 23) ([Shizuku.java](https://raw.githubusercontent.com/RikkaApps/Shizuku-API/master/api/src/main/java/rikka/shizuku/Shizuku.java), [Shizuku-API changelog](https://github.com/RikkaApps/Shizuku-API)).
- **Key methods:** `Shizuku.pingBinder()` (`binder != null && binder.pingBinder()`), `Shizuku.checkSelfPermission()`, `Shizuku.requestPermission(int)`, `Shizuku.shouldShowRequestPermissionRationale()`, `Shizuku.getVersion()`/`isPreV11()`, binder/dead listeners, `bindUserService`/`unbindUserService`/`peekUserService`, `Shizuku#getUid()` (0 = root, 2000 = ADB) ([Shizuku.java](https://raw.githubusercontent.com/RikkaApps/Shizuku-API/master/api/src/main/java/rikka/shizuku/Shizuku.java), [Shizuku-API README](https://github.com/RikkaApps/Shizuku-API)).
- **`UserServiceArgs`:** options `daemon(boolean)` (default **true** — "the service will run forever until `unbindUserService`"; non-daemon dies with the app process), `tag(String)` (identity of the service; class name if unset), `version(int)` (bump forces restart of the old instance), `debuggable(boolean)`, `processNameSuffix(String)` ([Shizuku.java](https://raw.githubusercontent.com/RikkaApps/Shizuku-API/master/api/src/main/java/rikka/shizuku/Shizuku.java)).
- **`ShizukuBinderWrapper` / `SystemServiceHelper`:** wrap a system-service Binder so `transact()` is executed by the privileged server; `SystemServiceHelper.getSystemService(name)` + generated `IPackageManager.Stub.asInterface(...)` is the canonical snippet on the front page ([shizuku.rikka.app](https://shizuku.rikka.app/), [ShizukuBinderWrapper source](https://github.com/RikkaApps/Shizuku-API/blob/master/api/src/main/java/rikka/shizuku/ShizukuBinderWrapper.java)).
- **AIDL files** (all under `aidl/src/main/aidl/moe/shizuku/server/`): `IShizukuService.aidl`, `IShizukuApplication.aidl`, `IShizukuServiceConnection.aidl`, `IRemoteProcess.aidl` ([repo tree via GitHub API](https://api.github.com/repos/RikkaApps/Shizuku-API/git/trees/master?recursive=1)). Note the interface is named **`IShizukuService`**, not `IShizuku`.
- **Legacy `newProcess`:** still present (`IRemoteProcess newProcess(cmd, env, dir) = 7`) but the changelog says "Prepare to remove `Shizuku#newProcess`, developers should have to use `UserService` instead" because it is text-based, slow and lacks tty support ([IShizukuService.aidl](https://raw.githubusercontent.com/RikkaApps/Shizuku-API/master/aidl/src/main/aidl/moe/shizuku/server/IShizukuService.aidl), [Shizuku-API changelog 13.1.1](https://github.com/RikkaApps/Shizuku-API)).
- **`rish` (interactive shell):** "`rish` is an Android program for interacting with a shell that runs on a high-privileged daemon process", with Shizuku and Sui as backends; `rish -c 'ls'` executes on the remote shell, and `RISH_PRESERVE_ENV` handles Termux PATH/LD_PRELOAD quirks (under an ADB backend defaults are tightened because ADB lacks permission to reach those places) ([rish/README.md](https://raw.githubusercontent.com/RikkaApps/Shizuku-API/master/rish/README.md)).
- **Developer options / boot-start:** see §3 — the manager stores launch mode and `start_on_boot`, and `v13.6.0` added "Support auto start without root on Android13+ when connected to a trusted WLAN" plus an updated start command ("You can copy this file to any executable location, such as `/data/local/tmp/shizuku`") ([v13.6.0 release notes](https://github.com/RikkaApps/Shizuku/releases/tag/v13.6.0)).

**How Shizuku differs from root (Magisk/KernelSU)**

- Root = uid 0 with a "do anything" SELinux context; ADB/Shizuku without root = uid **2000** with only the permissions Android grants the `shell` uid. `Shizuku#getUid()` returns 0 for root and 2000 for ADB, and "What ADB can do is significantly different from ROOT… Shell (ADB) cannot access other apps' data files `/data/user/0/<package>`" ([Shizuku-API README — Differents of the privilege](https://github.com/RikkaApps/Shizuku-API)).
- The authoritative list of what a Shizuku-ADB server may do is the Shell package manifest: [aosp-mirror `packages/Shell/AndroidManifest.xml`](https://github.com/aosp-mirror/platform_frameworks_base/blob/master/packages/Shell/AndroidManifest.xml) (linked from Shizuku's README; permissions vary per Android version).
- **Magisk** self-describes as "The Magic Mask for Android" (systemless root) ([GitHub API](https://api.github.com/repos/topjohnwu/Magisk)); Sui "requires an unlocked bootloader" because Magisk does ([Shizuku-API README](https://github.com/RikkaApps/Shizuku-API)). Shizuku, by contrast, works on **non-rooted** devices — with the catch that the server must be restarted after every reboot ([Shizuku-API README](https://github.com/RikkaApps/Shizuku-API), [setup guide](https://shizuku.rikka.app/guide/setup.html)).

**How Shizuku differs from LSPosed/Xposed**

- **LSPosed** is "A Riru / Zygisk module trying to provide an ART hooking framework which delivers consistent APIs with the OG Xposed", for "Android 8.1 ~ 14" — it *hooks* code in memory, typically requiring root/Magisk ([LSPosed README](https://github.com/LSPosed/LSPosed)). Shizuku does not hook anything: it performs ordinary Binder transactions from a privileged helper process, so it needs no bootloader unlock on Android 11+ (wireless debugging) but cannot change app/system behaviour the way an Xposed module can.

**How Shizuku differs from traditional `adb` usage**

- With plain `adb` you get a shell (uid 2000) you drive from a terminal; Shizuku keeps that shell-privileged *process alive* and exposes it to apps over Binder with a consent dialog, so "to the app, it is almost identical to the use of system APIs directly" ([README](https://github.com/RikkaApps/Shizuku), [introduction](https://shizuku.rikka.app/introduction.html)).

**Adjacent projects (not Shizuku itself)**

- **Dhizuku** ([iamr0s/Dhizuku](https://github.com/iamr0s/Dhizuku), 3,898★): "A tool that can share DeviceOwner permissions to other application" — a device-owner-based alternative/parallel backend some apps (e.g. ShizukuPlus) support ([GitHub API](https://api.github.com/repos/iamr0s/Dhizuku)).
- **App Ops** ([Play Store](https://play.google.com/store/apps/details?id=rikka.appops)) and **Storage Isolation** (`moe.shizuku.redirectstorage`) are Rikka's own apps listed alongside Shizuku on the Play developer page; App Ops' listing says "Shizuku integration makes it incredibly smooth to use without needi[ng root]" ([Play Store](https://play.google.com/store/apps/details?id=rikka.appops)).

## 7. Permissions and roles

- **Manager app identity:** package `moe.shizuku.privileged.api`, application class `ShizukuApplication`, with `MainActivity`, `RequestPermissionActivity`, `AdbPairingService`, `BootCompleteReceiver`, `ShizukuReceiver` and a `ShizukuManagerProvider` (`${applicationId}.shizuku`) ([manager AndroidManifest.xml](https://raw.githubusercontent.com/RikkaApps/Shizuku/master/manager/src/main/AndroidManifest.xml)). `ServerConstants.MANAGER_APPLICATION_ID = "moe.shizuku.privileged.api"` ([ShizukuService.java](https://github.com/RikkaApps/Shizuku/blob/master/server/src/main/java/rikka/shizuku/server/ShizukuService.java)).
- **Permissions the manager defines:**
  - `moe.shizuku.manager.permission.MANAGER` — `protectionLevel="signature"`; apps that request it get the Binder handed over automatically when the grant is present ([manifest](https://raw.githubusercontent.com/RikkaApps/Shizuku/master/manager/src/main/AndroidManifest.xml), [BinderSender.java](https://github.com/RikkaApps/Shizuku/blob/master/server/src/main/java/rikka/shizuku/server/BinderSender.java)).
  - `moe.shizuku.manager.permission.API_V23` — `protectionLevel="dangerous"` in permission group `moe.shizuku.manager.permission-group.API`; this is what `ShizukuProvider` uses (`ShizukuProvider.PERMISSION = "moe.shizuku.manager.permission.API_V23"`) ([manifest](https://raw.githubusercontent.com/RikkaApps/Shizuku/master/manager/src/main/AndroidManifest.xml), [ShizukuProvider.java](https://github.com/RikkaApps/Shizuku-API/blob/master/provider/src/main/java/rikka/shizuku/ShizukuProvider.java), [provider manifest](https://raw.githubusercontent.com/RikkaApps/Shizuku-API/master/provider/src/main/AndroidManifest.xml)).
- **What client apps declare:** only the `ShizukuProvider` entry (see §3) plus, optionally, the `dev.rikka.shizuku:provider` dependency; from v11 the access permission is **self-implemented** by Shizuku with runtime-permission-like semantics rather than a system permission the app applies for ([demo manifest](https://raw.githubusercontent.com/RikkaApps/Shizuku-API/master/demo/src/main/AndroidManifest.xml), [Shizuku-API migration guide](https://github.com/RikkaApps/Shizuku-API)). The `moe.shizuku.manager.permission.API` name survives only on a legacy activity ([manifest](https://raw.githubusercontent.com/RikkaApps/Shizuku/master/manager/src/main/AndroidManifest.xml)).
- **Manager's own privileged grants:** the server grants the manager `WRITE_SECURE_SETTINGS` at `attachApplication` time (which is what enables the Android 13+ ADB boot start) ([ShizukuService.java](https://github.com/RikkaApps/Shizuku/blob/master/server/src/main/java/rikka/shizuku/server/ShizukuService.java)); the manager also *uses* `RECEIVE_BOOT_COMPLETED`, `FOREGROUND_SERVICE`, `POST_NOTIFICATIONS`, `WRITE_SECURE_SETTINGS` ([manifest](https://raw.githubusercontent.com/RikkaApps/Shizuku/master/manager/src/main/AndroidManifest.xml)).
- **User service vs binder service:** a *Binder* call is a one-way privileged transaction proxied through `ShizukuBinderWrapper` (limited to what Binder calls allow); a *User Service* is a whole process running your code as root/shell, started with `bindUserService` and identified/stopped as described in §3 ([Shizuku-API README](https://github.com/RikkaApps/Shizuku-API)).

## 8. Use cases, advantages, limitations and risks

**Use cases (as documented by the project and adopters):** enable/disable components and other `PackageManager`/system operations without `pm` text parsing ([README](https://github.com/RikkaApps/Shizuku)); silent APK installation ([InstallWithOptions](https://github.com/zacharee/InstallWithOptions)); uninstalling/disabling system apps without root ([Canta](https://github.com/samolego/Canta)); permission/app management ([App Ops](https://play.google.com/store/apps/details?id=rikka.appops), [Inure](https://github.com/Hamza417/Inure)); F-Droid client privileged installs ([Droid-ify](https://github.com/Droid-ify/client/blob/main/README.md)); interactive privileged shell via `rish` ([rish README](https://raw.githubusercontent.com/RikkaApps/Shizuku-API/master/rish/README.md)).

**Advantages:** minimal overhead (no per-command process spawn, no text parsing, near-native API ergonomics) ([introduction](https://shizuku.rikka.app/introduction.html)); works without root/unlocked bootloader on Android 11+ via wireless debugging ([setup guide](https://shizuku.rikka.app/guide/setup.html)); one installation serves many apps ([Play listing](https://play.google.com/store/apps/details?id=moe.shizuku.privileged.api)).

**Limitations / risks:**

- **Not root.** ADB-privileged Shizuku only has the shell uid's permissions; the permission set is version-dependent and published in the Shell manifest ([Shizuku-API README](https://github.com/RikkaApps/Shizuku-API), [AOSP Shell manifest](https://github.com/aosp-mirror/platform_frameworks_base/blob/master/packages/Shell/AndroidManifest.xml)).
- **Restart after reboot** is required on non-rooted devices ("Due to system limitations, the startup steps need to be performed again after each reboot"); wireless-debugging start needs Android 11+, computer start covers Android 10 and below ([setup guide](https://shizuku.rikka.app/guide/setup.html), [Shizuku-API README](https://github.com/RikkaApps/Shizuku-API)). On-device ADB auto-start at boot exists only on **Android 13+** (see §3), and `v13.6.0` adds auto start on a trusted WLAN for Android 13+ ([BootCompleteReceiver.kt](https://github.com/RikkaApps/Shizuku/blob/master/manager/src/main/java/moe/shizuku/manager/receiver/BootCompleteReceiver.kt), [v13.6.0 notes](https://github.com/RikkaApps/Shizuku/releases/tag/v13.6.0)).
- **Hidden API restrictions** apply from Android 9 for code running in the app's own process — bypass via [AndroidHiddenApiBypass](https://github.com/LSPosed/AndroidHiddenApiBypass) or run logic in a User Service (where "There are no restrictions on non-SDK APIs") ([README — Attention](https://github.com/RikkaApps/Shizuku), [Shizuku-API README](https://github.com/RikkaApps/Shizuku-API)).
- **Android 8.0 caveat:** ADB lacks `registerUidObserver` permission there, so binder delivery to non-Activity processes is unreliable — the README recommends triggering delivery with a transparent activity ([README — Attention](https://github.com/RikkaApps/Shizuku)).
- **Device/OEM caveats:** the FAQ documents manufacturer interference (MIUI, ColorOS, Flyme, EMUI, GrapheneOS "Secure app spawning") that blocks pairing or randomises server stops ([setup guide — FAQ](https://shizuku.rikka.app/guide/setup.html)).
- **Security model:** any app granted permission can perform Binder transactions (or run User Service code) as shell/root on the device — hence the explicit consent dialog, per-UID `ClientRecord.allowed` state, and `SecurityException` enforcement ([Service.java](https://raw.githubusercontent.com/RikkaApps/Shizuku-API/master/server-shared/src/main/java/rikka/shizuku/server/Service.java)).
- **It cannot:** change app behaviour in memory (that's Xposed/LSPosed), read other apps' private data when running under ADB (shell uid restrictions), or survive reboots without root/Android 13+ auto-start ([Shizuku-API README](https://github.com/RikkaApps/Shizuku-API)).

## 9. Getting started (official flow)

1. **Install** from Google Play, GitHub Releases, Coolapk or the IzzyOnDroid F-Droid repo ([download page](https://shizuku.rikka.app/download.html), [websites source](https://github.com/RikkaApps/websites/blob/master/shizuku/download.md), [IzzyOnDroid](https://apt.izzysoft.de/fdroid/index/apk/moe.shizuku.privileged.api)).
2. **Enable Developer options** (tap "Build number" repeatedly) and **USB debugging** ([setup guide](https://shizuku.rikka.app/guide/setup.html)).
3. **Start:**
   - *Wireless debugging (Android 11+):* enable Wireless debugging → in Shizuku tap start → "Pair device with pairing code" → enter the code in Shizuku's notification (pairing is one-time) → start ([setup guide](https://shizuku.rikka.app/guide/setup.html)).
   - *Computer (Android ≤10):* install Google platform-tools, `adb devices`, then `adb shell sh /sdcard/Android/data/moe.shizuku.privileged.api/start.sh` ([setup guide](https://shizuku.rikka.app/guide/setup.html)).
   - *Root:* start directly in the app ([setup guide](https://shizuku.rikka.app/guide/setup.html)).
4. **Use from an app:** add `dev.rikka.shizuku:api` + `dev.rikka.shizuku:provider`, declare `ShizukuProvider`, call `Shizuku.checkSelfPermission()` / `requestPermission()`, then use `ShizukuBinderWrapper` or `bindUserService` ([Shizuku-API README](https://github.com/RikkaApps/Shizuku-API)).
